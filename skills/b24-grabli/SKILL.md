# Грабли Битрикс24 из практики

Общее почти у всех пунктов: ошибки нигде нет. Робот отработал, стадия сменилась, журнал
зелёный, а поле пустое или заявка ушла не туда. Ловится только прогоном с проверкой значения.

## Смарт-процессы: счётчики и справочники

- Список в смарт-процессе и одноимённый список в контакте — разные справочники. Робот копирует
  номер значения, получатель его не находит и очищает поле. Передавать подпись:
  `{=Document:UF_CRM_XX_FIELD_printable}`.
- Множественное поле без `MergeMultipleFields` замещается, а не дополняется. Флаг общий на
  робота, поэтому запись в множественное поле выносить отдельным роботом.
- Робот чтения чужой карточки может не вернуть значение, и тогда «прочитанное + 1» всегда даёт 1.
  Счётчик по своему же полю (`= {=Document:поле} + 1`) работает. Проверка за две минуты:
  выставить в карточке 5 и посмотреть, станет 6 или 1.
- Триггер по изменению поля не видит перехода «пусто → 0». Числовые поля, по которым решают
  триггеры, заполнять при создании карточки.
- Типы полей должны совпадать по обе стороны переноса (привязка к контакту ≠ сотрудник портала).
- REST не проверяет существование значения списка: чужой ID сохраняется молча, тест зеленеет на
  неверных данных. Значения брать из `crm.item.fields` (`items`) и
  `crm.contact.userfield.list` (`LIST`), не зашивать.
- Служебная стадия учёта считает при каждом входе, а карточку в неё можно перетащить руками.
- Ответ «ок» при заливке правки в дизайнер роботов не значит «сохранилось»: робот у стадии со
  сложной веткой условий сервер молча отбрасывает. Проверять перечитыванием после перезагрузки.
- Обращение через точку к полям связанного контакта не работает: документ смарт-процесса отдаёт
  только `CONTACT_ID`/`CONTACT_IDS`.
- Несколько воронок в одном СП → карточка показывает все поля разом. Раскладка задаётся на
  воронку: `crm.item.details.configuration.set` со `scope: 'C'` и `extras: {categoryId}`. Список
  полей брать из `crm.item.fields`: у воронки без раскладки текущая настройка пустая, запишешь
  пустую карточку.

Что проверять на любом проекте: записался ли списочный реквизит в связанную карточку;
накапливается ли счётчик со второго раза; дополнилось или заместилось множественное поле;
граничный случай «единица» (одна ставка, один участник, одно продление).

## Поля-списки через REST

- Значения справочника в смарт-процессе через `userfieldconfig.add/update` не заводятся никак:
  перебраны `list`, `LIST`, `enum`, `ENUM`, `settings.LIST`, `n0/n1` — поле создаётся, `enum: []`.
- Если значение рождается в коде, а не выбирается человеком, — делать поле строкой. Фильтр в
  канбане по строке работает. Список оставлять там, где значения правит человек руками.
- Обход для больших справочников: под сессией админа POST на `/bitrix/tools/uf.php`
  (`mode=main.edit&action=add`, `FIELDS[0][ENUM][i][VALUE]`, `FIELDS[0][SIGNATURE]`). Подпись лежит
  в `BX.Crm.EntityEditor` **внутри iframe карточки** (`document.querySelector("iframe").contentWindow`),
  в верхнем окне её нет. `action=update` значения игнорирует — поле пересоздавать.

## Бизнес-процессы и согласования

- **Начальник по оргструктуре раздваивает маршрут.** `GetUserActivity` с типом «руководитель» ищет
  начальника по каждому подразделению сотрудника. Два отдела у автора → два утверждающих → два
  задания на одном шаге («БП задваивается»). Чинить в оргструктуре, а не в схеме.
- Пустой `UF_HEAD` отдела сам не обрывает процесс — поиск поднимается к родительскому отделу. Но
  `UF_HEAD`, указывающий на удалённого пользователя, даёт задание без исполнителя: заявка стоит
  вечно. Ловится сверкой `department.get` → `user.get` → `bizproc.task.list`.
- **Согласующий часто берётся из оргструктуры, а не из шаблона.** Менять его в дизайнере
  бесполезно — переключатель в поле «Руководитель» подразделения.
- **Запущенный экземпляр доигрывает по старой версии шаблона.** Правка согласующего действует
  только на новые заявки. Хвост на старом человеке снимается `bizproc.task.delegate`
  (`TASK_IDS[0]`, `FROM_USER_ID`, `TO_USER_ID`) — история и вложения целы, процесс не
  перезапускать. Метод делегирует и `RequestInformationActivity`, и с несуществующего пользователя.
- `STATUS` в `bizproc.task.list`: `0` — живое, `1` — выполнено, `3` — истёк таймаут. Ставить
  `STATUS: 0` явно, иначе «находятся» закрытые задания.
- **«Отклонён ()» с пустыми скобками** — не отказ, а аварийно погасший процесс (зацикливание:
  пустая ветка «Исключение» после утверждения или не найденный начальник у деактивированного
  автора). Честный отказ: поле «Утверждён» = «Отказано», `USER_STATUS = 2`. Сбой: поле осталось
  «Не согласовано» и нет живого экземпляра в `bizproc.workflow.instance.list`.
- `bizproc.task.list` с `filter[DOCUMENT_ID]` отдаёт историю заданий даже по завершённым
  процессам — так восстанавливается маршрут мёртвой заявки.

## Аудит БП: где сидит сотрудник

- `bizproc.task.list` видит только шаги-задания. Он не видит «Поставить задачу» (`Task2`:
  ответственный, соисполнители, наблюдатели), уведомления, условия веток, `SetVariable`,
  «Выбор сотрудника». На вопрос «где участвует сотрудник» по нему одному отвечать нельзя.
- Дерево шаблона: `bizproc.workflow.template.list` с `select: ['TEMPLATE']`, либо глобальная
  `arWorkflowTemplate` на странице дизайнера `/bizproc/processes/{IBLOCK}/bp_edit/{ID}/`.
- `Users = ["author"]` у шага — человек получает задание как автор, вычищать бессмысленно.
- Журнал выполнения (`bp_log`) в облаке по умолчанию пуст.
- Новый БП в Списках: список и поля — REST (`lists.add`, `lists.field.add`), шаблон — только
  импорт `.bpt` в дизайнере. `bizproc.workflow.template.add` вебхуку не даётся
  (`Application context required`).

## Списки (lists.*)

- `lists.element.update` перезаписывает элемент целиком: непереданное стирается. Перечитать
  элемент и отдать все поля обратно. Файлы (тип F) сохраняются, если их не передавать. Пустое
  обязательное поле блокирует запись.
- `lists.element.get` со `start` за концом списка снова отдаёт последнюю страницу — цикл «пока
  есть элементы» не кончается и жжёт лимит. Останавливаться по `total` и повтору ID.
- `DATE_CREATE` в `lists.element.get` не отдаётся — свежесть считать по ID.

## Роботы, формы, задачи

- Робот «Изменить ответственного» с «пропускать завершивших рабочий день» раздаёт заявки только
  тем, кто нажал «Начать рабочий день». Никого на смене — заявка молча остаётся на создателе.
  Тестировать с открытой сменой (`timeman.open`).
- Новые CRM-формы не умеют скрытые поля и подстановку из параметра ссылки (`?partner=`).
  Служебное значение — только `presetFields` через `crm.form.save` под сессией
  (`crm.form.update` в REST нет). Телефон по умолчанию подставляет код страны по IP правящего,
  галка согласия 152-ФЗ создаётся отмеченной.
- «На сотрудника упало 1000 задач» — обычно счётчик непрочитанных комментариев, а не задачи.
  Первым делом `tasks.task.counters.get` с `userId`.

## Интеграции

- Переименовали облачный портал → `NO_AUTH_FOUND`. Приложение стучится на старый домен: обновить
  `domain` в своей таблице порталов, токены привязаны к `member_id`. Два экземпляра сервиса на
  одном refresh-токене отбирают доступ друг у друга.
- 403 `unsupported_country_region_territory` от OpenAI — сетевая беда (упал VPN), а не битый
  запрос. Внутри 4xx разбирать по коду в теле ответа, иначе письма теряются без повтора.
